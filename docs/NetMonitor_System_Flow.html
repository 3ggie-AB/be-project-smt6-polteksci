1. Ringkasan Sistem

NetMonitor API adalah backend untuk sistem monitoring jaringan. Sistem menyimpan data user, session login, inventory device, status device, konfigurasi monitoring, alert, notifikasi, activity log, relasi topologi jaringan, prediksi ML, dan anomali ML.

API menggunakan pola REST. Endpoint publik hanya root, health check, dan login. Endpoint lain berada di bawah /api dan dilindungi middleware autentikasi berbasis session token. Token dikirim melalui header Authorization: Bearer <token> atau query access_token.

Gambaran Besar Alur Sistem
ClientFrontend atau API consumer
->
FiberRouting dan middleware
->
AuthValidasi session token
->
ControllerAuth, user, CRUD resource
->
GORMQuery dan preload relasi
->
MySQLPenyimpanan data

Tujuan Fungsional

  • Mengelola user dan hak akses.
  • Mengelola device jaringan dan layanan.
  • Menyimpan status performa device.
  • Menyimpan konfigurasi monitoring ping dan TCP.
  • Mengelola alert dan notifikasi.
  • Menyimpan topology link antar-device.
  • Menyimpan output prediksi dan anomali ML.

Karakter Sistem Saat Ini

  • Backend API, bukan worker monitoring aktif.
  • CRUD generik untuk mayoritas resource.
  • Session token disimpan di tabel sessions.
  • Database dibuat otomatis jika belum ada.
  • Schema dibuat dan disesuaikan melalui GORM AutoMigrate.

3. Flow Startup Aplikasi

Saat aplikasi dijalankan dengan go run ., binary Docker, atau go run ./cmd/server, sistem menjalankan flow startup berikut.

Startup Flow
1Load .env dan environment
->
2Validasi konfigurasi
->
3Buat logger dan signal context
->
4Ensure database MySQL
->
5Open GORM connection
->
6AutoMigrate tables
->
7Start Fiber server
  1. config.Load() membaca .env memakai godotenv, lalu fallback ke environment/default value.
  2. Jika APP_ENV=production, nilai JWT_SECRET tidak boleh tetap default. Catatan: flow auth saat ini memakai session token database, bukan JWT payload.
  3. database.Connect() membuka koneksi ke server MySQL tanpa memilih database, lalu menjalankan CREATE DATABASE IF NOT EXISTS.
  4. GORM membuka koneksi ke database target, mengatur connection pool, melakukan ping, lalu menjalankan AutoMigrate untuk semua model.
  5. Fiber app dibuat dengan timeout baca 10 detik, middleware recover, dan CORS.
  6. Route didaftarkan melalui routes.Register().
  7. Server listen pada :PORT, default :8080.
  8. Saat menerima SIGINT atau SIGTERM, aplikasi shutdown secara graceful dengan timeout 10 detik.

4. Flow Request API

Semua request masuk ke Fiber. Endpoint publik dapat langsung merespons, sedangkan endpoint protected melewati middleware autentikasi lebih dulu.

Endpoint Publik

Method Path Flow
GET / Mengembalikan nama aplikasi, deskripsi, status running, dan daftar endpoint utama.
GET /healthz Mengembalikan status ok, stack aplikasi, dan konfigurasi host/port/database MySQL.
POST /api/auth/login, /api/login Login user dan membuat session token.

Endpoint Protected

Protected Request Flow
1Client kirim request + token
->
2Middleware ambil Bearer token
->
3Cari session aktif di MySQL
->
4Simpan user di Locals
->
5Role check jika perlu
->
6Controller proses data

Query session memakai kondisi token = ? AND expired_at > now. Jika token kosong, salah, atau sudah expired, API membalas 401 Unauthorized.

5. Flow Autentikasi

Login

Login Flow
1Client kirim email + password
->
2Normalize email
->
3Cari user by email
->
4Validasi bcrypt atau bootstrap user pertama
->
5Generate random token
->
6Simpan session

Endpoint login menerima JSON berisi email dan password. Email diubah menjadi lowercase dan spasi dihapus. Jika email atau password kosong, API membalas 401.

Jika user tidak ditemukan dan tabel users masih kosong, sistem otomatis membuat user pertama dengan role SUPER_ADMIN. Password disimpan memakai hash bcrypt. Ini adalah flow bootstrap admin awal. Jika tabel sudah berisi user, login email yang tidak ditemukan akan gagal.

Token dibuat dari 48 byte random, dikodekan dengan base64 URL-safe tanpa padding, lalu disimpan pada tabel sessions bersama user_id, expired_at, dan created_at. Masa berlaku token mengikuti SESSION_TTL, default 24h.

Me

Endpoint GET /api/auth/me dan GET /api/me membaca user dari c.Locals("user") yang sudah diisi middleware auth, lalu mengembalikan data profil tanpa password.

Logout

Logout Flow
1Client kirim token
->
2Controller ambil Bearer token
->
3Delete row session by token
->
4Token tidak bisa dipakai lagi

6. Flow Otorisasi Role

Sistem memiliki tiga role: SUPER_ADMIN, ADMIN, dan USER. Role dicek setelah session token valid. Jika role user tidak termasuk daftar yang diizinkan, API membalas 403 Forbidden.

Area SUPER_ADMIN ADMIN USER
Login, logout, me Ya Ya Ya
List dan detail resource protected Ya Ya Ya
Create user Ya Ya Tidak
Update user Ya Ya Tidak
Delete user Ya Tidak Tidak
Create, update, delete resource selain user Ya Ya Tidak

7. Flow CRUD Resource

Hampir semua resource memakai ResourceController[T] generik. Controller ini menerima model GORM dan nama resource, lalu menyediakan operasi list, create, detail, update, dan delete.

Method Path Controller Flow Akses
GET /api/<resource> Ambil semua row dengan Preload(clause.Associations). Semua user login
POST /api/<resource> Parse JSON body ke model, lalu DB.Create. SUPER_ADMIN, ADMIN
GET /api/<resource>/:id Parse ID, ambil satu row dengan preload relasi. Semua user login
PUT/PATCH /api/<resource>/:id Ambil row, parse body ke map, hapus field id dan created_at, update row. SUPER_ADMIN, ADMIN
DELETE /api/<resource>/:id Ambil row, lalu DB.Delete. SUPER_ADMIN, ADMIN

Flow CRUD User Khusus

User memakai controller sendiri karena perlu hashing password dan normalisasi field. Create user mewajibkan name, email, dan password. Jika role tidak dikirim, default role adalah USER. Update user hanya mengubah field yang dikirim dan password baru akan di-hash ulang.

8. Flow Domain Monitoring

Bagian ini menjelaskan alur bisnis berdasarkan model dan endpoint yang tersedia. Implementasi saat ini adalah backend API penyimpanan data. Proses ping, TCP check, pengiriman notifikasi eksternal, atau inferensi ML dapat dilakukan oleh frontend, worker, scheduler, atau service lain yang mengonsumsi API ini.

8.1 Inventory Device

Device Inventory Flow
1Admin tambah device
->
2Simpan name, IP, type, vendor, location
->
3Status awal ONLINE, OFFLINE, atau WARNING
->
4Device menjadi referensi status, alert, topology, ML

Device memiliki tipe AP atau SERVICE. Status device memakai enum ONLINE, OFFLINE, dan WARNING.

8.2 Monitoring Config

Monitoring Config Flow
1Admin pilih device
->
2Aktifkan ping atau TCP
->
3Tentukan interval dan port
->
4Config menjadi acuan proses monitor eksternal

Konfigurasi menyimpan ping_enabled, tcp_enabled, ping_interval, tcp_interval, dan monitored_port. Default ping aktif, TCP tidak aktif.

8.3 Device Status

Device Status Flow
1Monitor membaca config
->
2Monitor mengukur latency, packet loss, CPU, memory
->
3Data dikirim ke /api/device-status
->
4Status tersimpan untuk dashboard dan analisis

Tabel device_status menyimpan metrik numerik dan last_seen. Relasinya ke devices memakai device_id.

8.4 Alert

Alert Flow
1Rule atau operator mendeteksi masalah
->
2Buat alert untuk device
->
3Set severity INFO, WARNING, CRITICAL
->
4Status ACTIVE atau RESOLVED

Alert menghubungkan masalah ke device tertentu, menyimpan pesan, severity, status, dan waktu pembuatan.

8.5 Notification

Notification Flow
1Alert dibuat
->
2Sistem atau admin membuat notification
->
3Notification diarahkan ke user
->
4User membaca, field is_read diperbarui

Notification menyimpan user_id, alert_id, judul, pesan, status baca, dan waktu dibuat.

8.6 Activity Log

Activity log menyimpan jejak aktivitas user, misalnya CREATE_DEVICE, UPDATE_ALERT, atau aktivitas administratif lain. Model menyediakan field user_id, action, description, dan created_at. Pencatatan otomatis belum dipasang sebagai middleware, sehingga data log saat ini dibuat melalui endpoint CRUD.

8.7 Network Topology

Topology Flow
1Pilih source device
->
2Pilih target device
->
3Tentukan relation type
->
4Simpan status link untuk visualisasi topology

Topology menyimpan hubungan antar dua device menggunakan source_device_id dan target_device_id. Contoh relation type adalah uplink, sedangkan status dapat berisi nilai seperti active atau inactive.

8.8 ML Prediction dan ML Anomaly

ML Observability Flow
1Data status historis dianalisis
->
2Service ML membuat prediction atau anomaly
->
3Hasil disimpan via API
->
4Dashboard membaca hasil untuk insight

ml_predictions menyimpan tipe prediksi, nilai prediksi, dan confidence score. ml_anomalies menyimpan anomaly score, ringkasan prediksi, dan severity WARNING atau CRITICAL.

9. Flow Database dan Relasi Data

Semua model didaftarkan di ModelsForMigration() sehingga GORM membuat atau memperbarui tabel saat startup. Relasi memakai foreign key dengan constraint cascade update/delete pada model yang memiliki relasi eksplisit.

Tabel Field Utama Relasi
users id, name, email, password, role, created_at Menjadi parent untuk session, notification, activity log.
sessions id, user_id, token, expired_at, created_at user_id ke users.id.
devices id, name, ip, type, vendor, location, status Parent untuk status, config, alert, topology, prediction, anomaly.
device_status device_id, latency, packet_loss, cpu_usage, memory_usage, last_seen device_id ke devices.id.
monitoring_configs device_id, ping_enabled, tcp_enabled, ping_interval, tcp_interval, monitored_port device_id ke devices.id.
alerts device_id, severity, message, status, created_at device_id ke devices.id.
notifications user_id, alert_id, title, message, is_read user_id ke users.id, alert_id ke alerts.id.
activity_logs user_id, action, description, created_at user_id ke users.id.
network_topology source_device_id, target_device_id, relation_type, status Dua relasi ke devices.id.
ml_predictions device_id, prediction_type, prediction_value, confidence_score device_id ke devices.id.
ml_anomalies device_id, anomaly_score, prediction, severity device_id ke devices.id.
Saat controller list/detail menjalankan preload association, response dapat membawa object relasi seperti device, user, alert, source_device, atau target_device jika relasi tersedia.

->

->

->

Dockerfile memakai multi-stage build: stage pertama memakai image Go Alpine untuk build binary /out/netmonitor, stage runtime memakai Alpine, membuat user non-root appuser, lalu menjalankan /app/netmonitor.

Catatan: docker-compose.yml mereferensikan file ./migrations/001_mysql_observability.sql, tetapi folder/file tersebut tidak terlihat di working tree saat dokumen ini dibuat. 12. Error Handling dan Response

Controller memakai format response JSON yang konsisten. Jika operasi berhasil, response biasanya memakai field data atau message. Jika gagal, response memakai field error dan kadang detail.

Kondisi Status Response
Body JSON tidak valid 400 {"error":"invalid request body","detail":"..."}
ID URL tidak valid 400 {"error":"invalid id","detail":"..."}
Login gagal 401 {"error":"email or password is invalid"}
Token kosong 401 {"error":"authentication token is required"}
Token salah atau expired 401 {"error":"authentication token is invalid or expired"}
Role tidak cukup 403 {"error":"insufficient permission"}
Data tidak ditemukan 404 {"error":"resource not found"}
Error database/server 500 {"error":"failed to ...","detail":"..."}

Contoh Flow API Singkat

POST /api/auth/login
Content-Type: application/json

{"email":"admin@example.com","password":"secret123"}

Response:
{
  "message": "login berhasil",
  "token": "SESSION_TOKEN",
  "session": {...},
  "user": {...}
}
GET /api/devices
Authorization: Bearer SESSION_TOKEN

Response:
{
  "data": []
}

13. Catatan Implementasi

  • Auth saat ini memakai session token random yang disimpan di database, bukan JWT signed token.
  • JWT_SECRET tetap ada di konfigurasi dan divalidasi untuk production, tetapi belum dipakai dalam flow auth.
  • CRUD generik tidak memvalidasi aturan bisnis khusus per resource selain validasi constraint database dan parsing body.
  • Monitoring aktif, scheduler ping/TCP, notifikasi eksternal, dan mesin ML belum terlihat sebagai service di repo ini.
  • Activity log belum otomatis dibuat dari setiap aksi; endpoint CRUD tersedia untuk menyimpan log.
  • File README.md dan NetMonitor_API_Spec.md tercatat terhapus di working tree saat dokumen ini dibuat; isi versi Git terakhir dipakai sebagai referensi tambahan.
